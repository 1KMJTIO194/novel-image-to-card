# 人物分层 · 实现说明

按**剧情占比**把人物分成 主角 / 主要NPC / 次要NPC / 路人NPC 四档，并让这个分层真正影响产出：
谁进变量树、条目写多详细、世界里怎么标注。

---

## 一、为什么要重做

原来只有「主角 / 主要配角 / 次要配角 / 提及」四档，而这四档**完全是模型自己说的**：

- 没有任何客观依据 —— 同一本书换个模型、甚至同一模型换个温度，分层就可能不一样；
- 「配角」这个词本身有歧义 —— 既指"戏份很多的二号人物"，也指"只出现一次的路人"；
- 后果直接落在三处：**变量树给谁建好感度、状态栏显示谁、人物条目写多详细**。

典型症状：一张卡给只出场一次的路人写了 1200 字档案、建了好感度变量，
而真正的二号人物档案反而更短 —— 因为模型把两者都归成了「主要配角」。

## 二、核心做法：占比由原文算，模型只给提示

```
量：storyRatio = 该角色出现在多少比例的**章节**里
层：主要 ≥30% / 次要 ≥10% / 其余路人
主角：由 userMode 判定，不看占比
兜底：没有章节可统计时，才用模型给的 role
```

### 为什么用「章节占比」而不是「提及次数」

提及次数会被一段集中对话灌爆：某个路人只要在茶楼里跟主角聊上 30 句，
次数就能压过贯穿全书的二号人物。**章节覆盖率天然抗这个** —— 戏份分散在多章才算重要。

同一章里出现 100 次也只算 1 章，这是刻意的（`countChaptersPresent` 按章去重）。

### 为什么主角不看占比

群像作品里主角可能只占 15%，那份占比不该把它降级成次要NPC。
主角由 `userMode` 判定（Step 0.5 的叙事结构探测，或用户手选），优先级最高。

### 为什么模型提示只做兜底

模型很擅长判断"这两个名字是不是同一个人"，但**不擅长数比例**。
所以比例由代码算好，模型只在"没有章节可统计"（单块文本、统计失效）时兜底。

## 三、分层如何影响产出

| 位置 | 影响 |
| --- | --- |
| 变量树 | 主角 / 主要NPC / 次要NPC 建 `affinity` + `state`；**路人NPC 不建** |
| 人物档案 | `TIER_DETAIL` 决定 prompt 里要求写多详细 |
| 世界书条目 | 注释写成 `[character] 名` 或 `[character·主要NPC] 名` |
| 条目 extensions | `tier` / `storyChapters` / `storyRatio` 三个结构化字段 |
| meta.json | `counts.tiers` 给出各档人数 |

**路人NPC 不建变量**的理由：它们在原文里往往只被提一两次，给它们立好感度只会污染变量更新规则 ——
AI 每轮都要在这些"永远不会变化的字段"上做无用判断，还容易写错路径。

## 四、踩过的坑

### 1. 注释格式改了，读取侧全挂

人物条目注释从 `[character] 名` 变成 `[character·主要NPC] 名` 之后，
所有用 `startsWith('[character]')` 或 `comment === '[character] 名'` 精确匹配的地方全部失效。

实际后果：`augment.js` 的 `extractCardStructure` 把人物条目**全部漏掉** ——
增补功能看到"原卡里没有人物"，于是把已有角色又新增了一遍。

修法：把注释的读写收进 `src/tiers.js`（`characterComment` / `isCharacterComment` /
`tierFromComment` / `extractName` 配合），读取侧一律走这些函数。

### 2. 跨批的章节数：求和还是取最大

分批评析下，同一个人物在不同批次里各有一条记录：

- **各批的章节互不相交** → 跨批要**求和**（横跨 11 批的角色不能被算成只出场 1 批）；
- **同一批里的同名重复条目**（模型把一个人抽了两次）→ 要**取最大值**。

这两个需求同时存在，所以按批号分桶记 `Map<batchIndex, 章节数>`，
同批取 max、跨批求和。早期版本先写成 `acc.storyChapters += r.storyChapters`（同批重复会翻倍），
改成标量取 max 后又把跨批的戏份丢了 —— 两次都踩过。

### 3. 循环依赖

`merge_batches.js` 在**模块顶层**读 `pipeline.js` 的 `TIER_RANK`：
`data-layer.mjs → pipeline.js → merge_batches.js → pipeline.js`（未求值完），
报 `Cannot access 'TIER_RANK' before initialization`。

修法：档位常量与纯函数独立成 `src/tiers.js`（无依赖），两边都只依赖它。

### 4. `role` 在归并阶段不能提前写成分层

归并的「主名优选」需要知道**模型给的等级提示**（用它区分「林昭(主角)」与「阿昭(次要NPC)」）。
如果 `sanitizeRoster` 一上来就把 `role` 覆盖成分层值、或归并时统一塞默认值，
主名优选就会失去依据。所以：

- 归并阶段：`role` 保留提示值（旧档位名用 `normalizeTier` 映射）；
- Step 5 分层之后：`role` 写回实测 `tier`，这才是最终值。

### 5. 测试不能用单字名

`appearsInTextLoose` 对单字有最短长度保护（单字命中率太低，全是假阳性），
所以测试里的「甲」「乙」一律匹配不上，分层全落到"0 章"。
测试用两个字以上的真名（林昭 / 沈砚 / 周管事）。

## 五、实测（假 LLM，12 章）

```
规划：林昭 12 章(100%) / 沈砚 6 章(50%) / 周管事 2 章(17%) / 卖花老人 1 章(8%)
[Step 5]   主要NPC 1 人：沈砚(6章/50%)
[Step 5]   次要NPC 1 人：周管事(2章/17%)
[Step 5]   路人NPC 1 人：卖花老人(1章/8%)

A 包人物条目：
  [character] 林昭              tier=主角     ch=12  ratio=1
  [character·主要NPC] 沈砚       tier=主要NPC  ch=6   ratio=0.5
  [character·次要NPC] 周管事     tier=次要NPC  ch=2   ratio=0.1667
  [character·路人NPC] 卖花老人   tier=路人NPC  ch=1   ratio=0.0833

变量树人物：["沈砚","周管事"]        ← 主角被 userMode 移出，路人被排除
meta.counts.tiers：{"主角":1,"主要NPC":1,"次要NPC":1,"路人NPC":1}
```

## 七、无法在本沙箱验证的

- **真机真 LLM 的分层质量**：全部用假 LLM，只能证明"占比算得对、分层落到了产出里"，
  不能证明真实长篇里 30%/10% 这两个阈值就是最合适的。阈值是**可调常量**
  （`src/tiers.js` 的 `TIER_THRESHOLDS`），真实用下来觉得偏了就改这两个数。
- **"路人NPC 不建变量"的边界感受**：阈值附近的人物（比如 9% 与 11%）会被分到不同档，
  实际体验上是否有"这个人明明挺重要却没变量"的情况，需要真实阅读才能判断。
- **`appearsInTextLoose` 对非常见称呼形式的召回**：别名没覆盖原文写法时，
  占比会算成 0，日志里会给出 `WARN`（"在原文里一次都没匹配到"）。
