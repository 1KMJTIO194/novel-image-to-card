# 图片生成角色卡：上限 8 → 60 + 分批处理

用户反馈：**「8 张有点少了，遇到一个长一点的漫画都生成不了」**

查下去发现不止一个 8 —— 真正卡住的是 **6**。

---

## 三处限制，而且互相不一致

| 位置 | 限制 | 说明 |
| --- | --- | --- |
| `public/js/pages/image-card.js` | **8** | 界面提示"最多 8 张" |
| `server.js` `/api/image-card` | `maxCount: 8` | multer 字段上限 |
| `server.js` 全局 `upload` 实例 | **`limits.files: 6`** | ← **真正的硬上限** |

`limits.files` 是 busboy 的**硬上限**，在按字段计数（`maxCount`）**之前**就触发。
所以实际行为是：

> **界面允许选 8 张，传到第 7 张就被拒**，报错还是 multer 原始的 `Too many files`。

也就是说 8 和 maxCount 全是摆设。这一点在修 `maxCount` 之后跑真实接口才暴露 ——
第一次改完仍然收到 `{"error":"Too many files"}`，因为 `files: 6` 先拦住了。

---

## 只放开上限是不够的

`extractCharactersFromImages` 原来把**所有图片塞进一次请求**：

```js
const raw = await llm.chat(S.STEP_IMAGE_TO_CARD, userText, 'image-vision', {
  images: valid.images.map(i => i.path),   // ← 全部
});
```

就算把上限放到 60，一次喂 60 张会：
- 超出模型的图片 / 上下文上限
- **每张图分到的注意力被稀释**，后面的页描述明显变差

所以改成**分批 + 并发 + 合并**：

| 参数 | 默认 | 理由 |
| --- | --- | --- |
| `MAX_IMAGES` | 60 | 每张约 1000-1500 image token，60 张 ≈ 6-9 万 token 视觉输入 |
| `DEFAULT_VISION_BATCH` | 6 | 一话漫画 20 页 → 4 批；每批张数少则分析细、多则注意力差 |
| `DEFAULT_VISION_CONCURRENCY` | 2 | 图片 token 贵，并发高了容易被上游限流 |
| `BATCH_ATTEMPTS` | 3 | 批次级重试（见下） |

### 全局「图N」编号

分批后每批的 `imageIndex` 都是"从 0 开始"的局部编号，
直接用的话第 3 批的人物会被标成「（图1）」—— 明明来自第 13 张图。

所以 `normalizeCharacterProfiles` 加了 `imageOffset`：

```js
// ⚠️ 顺序很重要：先按**本批**夹取越界下标，再加 offset
if (imageCount > 0) { /* 夹回本批范围 */ }
if (imageOffset) { for (const c of out) c.imageIndex += imageOffset; }
```

顺序反了（先加 offset 再按本批 imageCount 夹）会把后面所有批次夹回 0。
测试里专门钉了这条：越界下标 99 → 夹到 5 → 加 offset 12 = **17**。

### 跨批去重

每批内部已经去过重，但**同一个角色出现在多批里**是长漫画的常态（主角贯穿全书）。
同名档案会让变量树 `characters.<varKey(名)>` 塌成一个键（实测 2 个人物只剩 1 个），
所以合并后必须再按名字去重一次，用**全局**图号打「（图N）」。
抽成了纯函数 `mergeBatchProfiles` 以便测试。

## 实测（真实模型 deepseek-flash）

### 20 张图（一话漫画）

```
[Vision] 视觉抽取：20 张图，分 4 批（每批最多 6 张）
[Vision] 第 1/4 批完成：6 张图 → 6 条档案
[Vision] 第 2/4 批完成：6 张图 → 6 条档案
[Vision] 第 3/4 批完成：6 张图 → 6 条档案
[Vision] 第 4/4 批完成：2 张图 → 2 条档案
[Vision] 视觉抽取：20 条人物档案
[Assemble] 角色 20 人 / 世界书 5 条 / 状态栏主题 scifi / 36 条条目
```

- 耗时约 **39-44 秒**
- 20 张图 → **20 条人物档案**，无丢失
- 图号是全局的：`夜街行人剪影（左）（图3）` 确实来自第 3 张

## 中途发现并修掉的四个问题

### ① `limits.files: 6` 是真正的上限

见上。改成 `MAX_IMAGES + 8`（留余量给小说文件 / 卡片 / 头像）。

### ② multer 的原始报错用户看不懂

`Too many files` / `File too large` 完全看不出是哪里限的、限到多少。
加了错误处理器，换成可读文案：

```
图片数量超过上限：一次最多 60 张（长漫画请按话分批生成）
```

### ③ 「批次成功但没抽到人物」会静默丢内容

实测遇到一次：20 张图只出 **18 条**，第 4 批**没有报错**、返回了 0 条档案 ——
那 2 张图的内容就静默消失了。它不是"失败"（请求是成功的），
所以原来 `failedBatches` 那条分支发现不了。

现在单独统计 `emptyBatches`，日志与进度都会说：

```
[WARN] 有 1/4 批没有抽出人物档案 —— 那几页图未被利用
```

### ④ 图片路径的 `files` 事件少了 `taskId` 和 `summary`

生成页与完善页都在 `files` 事件里带 `summary`，图片路径**没带**，
所以图片生成完**不会 inline 显示变更总结**（要等前端再请求一次，
刷新页面还可能拿不到）。补上 `taskId` + `summary`，三条路径形状统一。

顺带补了 `renderSummaryMarkdown` 漏掉的 `source` 行 ——
图片路径的 `baseline` 是"从零生成"，而 **"由 20 张图片生成"只在 `source` 里**，
不渲染的话这句话在 SUMMARY.md 里看不到。

---

## 批次级重试

`llm.chat` 内部已有 3 次退避重试（1s/2s/3s），但那是**同一次调用内**。
实测遇到过整轮 4 批**全失败**（内部重试都跑完了仍全挂）。
长漫画 10 批时那种情况会让整轮报废，所以在批与批之间再加一层 `BATCH_ATTEMPTS = 3`。

---

## 界面

- 上限提示改为 **最多 60 张**
- 新增一行说明：**超过 6 张会自动分批送给模型（长漫画按话导入即可）**
- 新增「**③ 分批设置**」卡片：每批张数可调（1-12，默认 6），
  长漫画想更细可以调小。控件带 `id`/`name`/`label`，符合表单规范。

## 仍未验证

- **没跑过 60 张的完整流程**（只跑了 20 张）。60 张 = 10 批，按 20 张约 40 秒估算
  约 2-3 分钟，且上游限流风险随批数上升。分批逻辑本身与批数无关，但**未实测 10 批**。
- **未测超限时的真实接口报错**：`MAX_IMAGES + 1 = 61` 张的请求没实际发过。
  单元测试覆盖了 `validateImages` 的报错文案，multer 层的
  `LIMIT_FILE_COUNT` 分支（需要 > 68 个文件）也未实测。
- 每张图的 token 成本随尺寸变化，60 张的实际花费没有测过。
