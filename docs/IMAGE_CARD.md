# 图片生成角色卡

第三条入口（`#/image-card`）：**没有小说文本**时，靠图片生成一张可用的角色卡。
适合漫画截图、聊天记录、社交平台帖文、人物立绘、AI 出图。

## 总结图片里的信息 → 设定（`src/image_summary.js`）

**这是图片路径的正路。** 分两步，职责不同：

```
① 看图（STEP_IMAGE_TO_CARD）   → 抽出画面事实：外貌、服饰、场景、转录的文字
② 总结（STEP_IMAGE_SUMMARY）   → 把那些**信息**归纳成**设定**：人物、地点、势力、体系、舞台
③ 装配                          → 变量树 / 状态栏 / 世界书 / 完整角色卡
```

用户对这条路径的要求（原话）：

> 「通过图片生成角色卡应该是**总结图片里的内容信息**生成角色卡，
> 而不是**图片里面怎么怎么样**，**图片里发生了什么剧情**等。」

所以有两组**硬禁止**，prompt 里写死、代码里再兜一道清洗：

| 不要 | 例子 | 要 |
| --- | --- | --- |
| 指涉图片本身 | 「图中是一位银发少女，头像约 60 像素」 | 「银发少女，银灰长发垂至肩前」 |
| 把经过写成剧情 | 「事件1：寝室夜谈 → 事件2：关系确认」 | 「与同寝室室友关系复杂：从抗拒到逐渐接受」 |

具体做法：

- **prompt** 明令禁止「图片 / 画面 / 截图中 / 图中 / 头像 / 像素 / 构图」这类词，
  也禁止把资料里的经过列成事件；并规定**信息不足时省略字段**，
  而不是写「图片未提供」占位（否则卡就成了体检报告）。
- **代码兜底** `stripImageFraming()`：模型经常不听，所以对每个字段再做一次清洗
  （去掉句首引导语、把「（据画面推断）」收成「（推断）」、抹掉零散指涉词）。
  这一步是**保守**的 —— 只处理句首/分句首的引导语，不重写内容。
- **人物 YAML** 用 `renderSettingsYaml()` 渲染：写 name / identity / appearance /
  personality / relations… 这些**设定字段**，缺的字段直接省略。
  外貌缺失时用画面事实补（那是"看得见的"，不是"这是张图片"）。

**不抽剧情。** 图片路径**不产出**事件列表 / 故事线 / 阶段 ——
那些是小说路径的产物（长篇小说有章节与推进），图片给的是信息。
但状态栏与导演指令需要一个落点，所以只造**一个**「开场」，
内容来自总结里的 `scenario`（舞台处境），不是"发生了什么"。

## 与小说路径的差异

| | 小说路径 | 图片路径 |
| --- | --- | --- |
| 外貌 / 服饰 | 从文字描述提取 | **视觉分析**（更准） |
| 姓名 / 身份 / 关系 | 从原文提取 | **从信息总结**（截图文字里有就准） |
| 世界观（地点/势力/体系） | 从原文抽取 | **从信息总结** |
| 剧情事件 | 从章节抽取 | **不抽**（只给一个开场处境） |
| 时间线 | 有章节号与日期，可推世界日期 | **不做日期推断**（标 `approximate`） |

**绝不编造**：资料与画面都没有的设定不写。填一段「文字补充设定」能显著提升可用性。

设置项 `wantWorldbook` 关掉时不生成世界书条目。

## 生成档位：基础版 / 完整版（`src/detail_level.js`）

两档共用同一套流程，**只在"写多细"上做差分** —— 基础版就是原来的行为（token 不增加），
完整版才多花 token。

| | 基础版（默认） | 完整版 |
| --- | --- | --- |
| 人物档案 | 原样 | 模板字段尽量写全；`appearance ≥150 字`、`clothing ≥120 字`、`background ≥200 字`、`personality/言行举止 ≥120 字`；补 `relations / speechStyle / voiceSample` |
| 分层字数 | 主角 600 / 主要 400 / 次要 150 / 路人 0 | 主角 1000 / 主要 700 / 次要 260 / **路人仍是 0** |
| 世界观 | 原样 | 地理要能看出从属；每条 ≥120 字；势力/体系要写运作方式与影响 |
| 剧情概要 | ≤1200 字 | ≤2400 字，按时间顺序覆盖到当前进展，写清关系变化 |
| 图片路径精修 | 最多 3 个主要角色，每人 6 张图 | 最多 6 个，每人 8 张图 |
| 调用次数 | 不变 | 小说路径**不增加调用次数**（只是每次输出更长）；图片路径最多多 3 次带图请求 |

> 完整版**不给路人加量**：完整版的意义是把主要人物写透，不是给路人灌水 ——
> 一条 800 字的路人档案既浪费 token，又会在世界书里抢主要角色的注意力。

怎么用：生成页与图片页都有「生成档位」下拉；DSH 插件面板有同名下拉；
命令行加 `--full`；不传时一律按基础版（前端传了非法值也回落基础版，避免成本意外翻倍）。

## 反剧透：禁止推测未揭示的真相

用户要求「不要反转、伏笔、阴谋论」，实现方式是**一条可判定的约束**，而不是一串术语黑名单
（黑名单能被"实际上/原来"绕开）：

> 只写原文/资料里**已经明确说出**的内容。不要推测、补完或暗示尚未揭示的真相、
> 隐藏身份、幕后主使、后续转折；不要用「其实……」「真正的……」「幕后……」这类说法
> 给出结论。信息不足就写「未提及」，不要用推断去填。

这条**两档都加**（约 130 字，对成本影响很小），作用在：人物档案、世界观、剧情概要、
图片信息总结四处。

## 年龄 / 身高 / 体重 / 三围：必须出现在卡里

用户反馈（原话）：

> 「角色卡里生成的年龄身高和三围好像没出现明确的数值就不会填上去了」

原因是之前为了"不写占位废话"，这四个字段拿不到明确数值时**整行丢弃** ——
结果卡里完全看不到它们，人设显得不完整，也没法在 SillyTavern 里编辑补全。

现在的两段式策略：

| 环节 | 做法 |
| --- | --- |
| **prompt** | 这四项**必须给值**：有明确依据写实测；没有就按身份、年龄感、体型、画面比例给**推断值/区间**并标「（推断）」（如 `20-24 岁（推断）`、`约 162cm（推断）`、`B86-90/W60-64/H88-92（推断）`）；确实不适用才写「不适用」 |
| **渲染兜底** | 万一模型还是没给，渲染时写成 `未提供（可自行设定）` —— **字段一定在**，用户一眼知道该补什么 |

兜底只对**由资料总结出来的人物**生效（`renderSettingsYaml(..., { fillBasicStats: true })`）；
纯视觉路人（画面里出现、资料没提到）不开，否则一话漫画 20 多个路人每人多四行占位。

小说路径同理：`STEP_5_CHARACTER` 的模板里这四项已改成"有依据写实测 / 没依据给推断区间并标注"。

## 剧情条目按剧情段落生成（`src/event_segments.js`）

**修掉的真 bug**：事件条目正文原来全书只调 **1 次**，而喂给模型的原文节选是

```js
const excerpt = chunks.slice(0, 4) ...   // 只有前 4 章
```

一本 25 章的书，第 5 章以后的 60 多个事件条目，正文是靠"事件清单里一行 canon"编出来的
—— 模型根本没看过对应原文。用户的原话「剧情条目、地理条目根据剧情段落生成」正好点在这上面。

地理条目本来就是按批抽取的（每批一次调用，最后归并去重），所以这次只改剧情条目：

```
事件按批次（= 剧情段落）分组 → 每段一次调用，只喂该段原文
→ 归不进任何段落的事件用自己章节的原文兜底（不丢）
→ 剧情简介单独一次调用（输入只用事件清单 + 分批摘要，不塞原文）
```

| | 基础版（默认） | 完整版（默认按段） |
| --- | --- | --- |
| 事件条目调用 | 1 次（原文节选只有前 4 章） | 每段 1 次（该段完整原文） |
| 剧情简介 | 与事件条目合并调用顺带拿 | 单独 1 次（`STEP_5_SYNOPSIS`） |

**实测成本**（5.7 万字 / 25 章 / 3 批，确定性输入）：输入字符 **372,781 → 409,960（+10.0%）**，
调用 45 → 48 次。用 5 批的书大约 +7~8%，因为批次越多单批原文越短。

可用 `eventEntriesPerBatch: true/false` 强制开/关（默认跟档位走）；
高级选项在生成页/插件里没有单列开关，走 `options` 或 CLI 配置。

> 顺带确认：**「世界观 + 物品」合并抽取已经存在**（`mergeWorldCalls`，默认开），
> 同一段批正文只发一次，这块不需要再改。

## 角色卡版本：普通版 / 成人版（`src/content_mode.js`）

用户要求：既要有**不含成人内容的普通卡**，也要有**完整包含成人内容的成人卡**。

| | 普通版（默认） | 成人版 |
| --- | --- | --- |
| `erotic_abilities` / `私处细节描写` | **整段省略**（代码删除，不留空行） | 保留，要求写具体（敏感点、癖好、边界；私处按乳房/小穴/肛门三项） |
| `preferences` | 只写日常喜好与厌恶 | 可包含性偏好 |
| 其它字段 | 照常写细 | 照常写细 |
| 角色年龄 | 出场角色须成年 | 出场角色须成年；资料显示未成年的角色**不写**成人内容 |

**两条关键设计：**

1. **默认必须是普通版**。不传、传空、传乱值一律回落 `general` ——
   不能因为前端传错就让用户在不知情的情况下生成成人内容。
2. **普通版不能只靠 prompt**。模型经常无视"不要写"的指令，所以
   `stripAdultFieldsFromYaml()` 会在**落盘前**把成人字段从 `content_yaml` 里按行删掉
   （连同缩进子块），其余内容一个字不动 —— 不用 YAML 解析再序列化，避免改变格式或丢注释。
   小说路径在 `finalizeCharItem` 过这道闸门；图片路径在总结归一化与装配两处各过一道。

图片路径的特殊说明：画面能提供的是**可见事实**（体型、衣着、裸露程度），
提供不了"私处细节"这类设定。所以成人版里这些字段**只写转录文字明确提到的**，
没写到就写「未提及」—— 不编造。

怎么用：
- 生成页 / 图片页：都有「角色卡版本」下拉，默认普通版
- DSH 插件面板：同名下拉（默认普通版）
- 命令行：图片目录脚本加 `--adult`，不加即普通版
- 完善已有卡（augment）**不提供**这个选项：那是改用户已有的卡，不该改变它的性质

## 主要角色的定向档案（`src/char_excerpt.js`）

原实现里所有角色共用一份「全书均匀随机抽样」（`sampleAcrossText(text, 10000)`）：
所以"每个角色单独生成"只是把**同一份抽样多发几遍**，模型注意力集中了，但看到的原文并没有更相关。

完整版默认改成：**主要角色（主角 / 主要NPC）逐个生成，且只喂它真正出场的章节**。

```
按名字/别名在章节里检索出场章 → 首章 + 尾章 + 均匀取样（默认 6 章）
→ 每章按预算切一段，拼成 ~1 万字节选 → 一次档案调用
```

| | 基础版 | 完整版 |
| --- | --- | --- |
| 主要角色 | 与其余角色一起批量（共享全书随机抽样） | 逐个 + 按出场章节取样 |
| 次要/路人 | 批量 | 仍批量（逐个只会线性涨成本） |
| 开关 | `charMajorTargeted: true` 可开 | `charMajorTargeted: false` 可关 |

**实测成本**（5.7 万字 / 25 章 / 7 人物）：完整版 `409,960 → 469,956` 字符（**+14.6%**），
其中 5 个主要角色定向 + 其余批量。真实小说通常 1 主角 + 2~3 主要NPC，
对应约 **+7%**。定向人数上限由 `majorTargetedLimit`（默认 5）控制。

## 完善卡的人设整合（`STEP_AUGMENT_INTEGRATE`）

augment 原来的合并是**纯文本追加**：新剧情的人设变化以「【新增内容】」追加到条目末尾，
于是"关系变了 / 身份变了"这类变化会**前后矛盾地并存**。

现在（默认开启）：对"对齐器匹配到的已有人物条目"各跑一次整合调用：

```
旧条目正文 + 新剧情里该角色的新信息（重抽档案 + 阶段人设增量）
→ 更新后的完整 content_yaml（保留旧信息，冲突以新剧情为准）
```

| | 说明 |
| --- | --- |
| 成本 | 每个匹配角色 1 次调用（输入几 K 字符，无原文节选）；`integrateLimit` 默认 8 |
| 关闭 | 生成页「人设整合」勾选框 / DSH 插件同名勾选框 / `integrateCharacters:false` |
| 失败 | 不中断任务，保留追加合并结果，并记进 `report.integrateSkipped` |
| 报告 | `report.integrated`（整合成功的人名）、`updated[].how = 'integrated'` |
| append 策略 | 不改已有条目，因此也不会整合 |

## 图片路径的 token 记账（`mergeUsage`）

上轮 token 审计发现：图片卡的 `meta.usage` **只统计了视觉抽取**，
信息总结与外观精修用的是另外的 LLM 实例，没并进 meta → 图片卡成本被低估。

现在 `src/llm.js` 提供 `mergeUsage(...)`，Web 版与插件都会把
**视觉抽取 + 信息总结 + 外观精修** 三份记账合并进 `meta.usage`，
`byStep` 里能同时看到 `image-vision` / `image-summary` / `image-detail`。

## Token 消耗审计（`scripts/token-audit.mjs`）

想看"钱花在哪"、或者改配置前预估成本，不用再临时插桩：

```bash
npm run token-audit            # 审计 output/ 与插件数据目录里的真实任务 meta.json
npm run token-audit:sim        # 确定性模拟：对比各配置档位（不花钱、不需要 API Key）
node scripts/token-audit.mjs --simulate --chapters 25 --chars-per-chapter 2300
node scripts/token-audit.mjs --json   # 机器可读
```

真实任务模式会汇总：调用次数、输入/输出字符、估算 Token、**按步骤占比**、
失败任务浪费（输出为空但输入已发出），以及"总字符 / 原文字符"倍数。

模拟模式用假 LLM 跑完整流水线 —— 输入字符与真模型完全一致，只对比输入结构：

| 配置（5.75 万字 / 25 章 / 3 批） | 调用 | 输入字符 | ≈Token | 相对基础版 |
| --- | --- | --- | --- | --- |
| 基础版（默认） | 41 | 314,658 | ≈196,661 | — |
| 完整版（按段剧情 + 定向档案） | 47 | 387,327 | ≈242,079 | **+23.1%** |
| 完整版 · 关掉按段剧情 | 44 | 351,593 | ≈219,746 | +11.7% |
| 完整版 · 关掉定向档案 | 44 | 351,362 | ≈219,601 | +11.7% |
| 基础版 · 逐个生成档案 | 44 | 349,436 | ≈218,398 | +11.1% |

> 换算是经验值：中文约 **1.6 字符 / Token**。真实书跑下来总字符 ≈ 原文字符 × 5~11，
> 主要变量是章节数（决定批次）与人物数（决定档案调用数）。

## 角色卡格式：普通卡 / 完整卡（`src/card_format.js`）

用户要求：既能出**没有美化和变量的普通角色卡**，也能出**有美化和变量的完整角色卡**。

两个词在这里的定义（写清楚，免得歧义）：

| 词 | 指什么 |
| --- | --- |
| **美化** | 状态栏（HTML 状态面板）+ 卡内嵌的 7 条正则（正文美化 / 状态栏美化 / 状态栏纯文本 / 思维链隐藏 / 变量更新隐藏 …） |
| **变量** | MVU 变量树：`[initvar]勿启用`、`变量更新规则`、`变量更新强调`、`导演指令`、`角色阶段`，以及卡里注册 MVU 的 `tavern_helper` 脚本 |

| | 普通卡（`plain`） | 完整卡（`enhanced`，默认） |
| --- | --- | --- |
| 状态栏 + 正则 | 无 | 有（7 条） |
| 变量树 / 变量更新规则 / 导演指令 / 角色阶段 | 无 | 有 |
| `[initvar]勿启用` / 围栏与隔离 / 输出纪律 / 干预与偏离度 | 无 | 有 |
| 时间线、剧情简介、世界观、人物、事件、故事线 | **有** | 有 |
| 需要的扩展 | **无**（纯 ST 原生，导入即用） | 「酒馆助手」4.2.0+ 与「MVU」变量框架 |
| 状态栏那次 LLM 调用 | **跳过**（省一次请求） | 有 |
| 产物里的 `variables.json` / `statusbar.json` / `regex_scripts.json` / `statusbar_preview.html` | 不产出 | 产出 |

实现要点：

1. **默认仍是完整卡** —— 不传 `cardFormat` 时行为与以前完全一致，老用户不会被静默削弱。
2. **普通卡是完整卡的严格子集**：不是两条组装路径，而是在 `assembleCharacterCard()` 之后
   由 `makePlainCard()` 摘掉美化与变量。这样两档不会随各自改动而漂移 ——
   加新功能只会影响完整卡，普通卡永远等于"完整卡减去美化与变量"。
3. 普通卡的 `creator_notes` 会换成对应说明（不再提酒馆助手/MVU，只留"导入内嵌世界书"那一步）。

怎么用：
- 生成页 / 图片页：都有「角色卡格式」下拉，默认完整卡
- DSH 插件面板：同名下拉（默认完整卡）
- 命令行：图片目录脚本加 `--plain`，不加即完整卡
- 完善已有卡（augment）不提供该选项，理由同上

## 主要角色的外貌 / 服装精修（`src/image_detail.js`）

**要解决的问题**（用户反馈）：

> 「主要NPC的外貌服装注意力不足描写的不够详细有遗漏，
> 我觉得可以在区分主要NPC和次要NPC之后重点观察描写NPC的外貌和服装」

一次总结里模型要同时产出人物、世界观、舞台设定，**注意力被摊薄** ——
主要角色的外貌往往只剩一句"黑色长发、深色外套"。
而外貌与服装恰恰是**图片独有的信息**（文字资料里通常没有）。

所以流程改成三步：

```
① 看图      → 画面事实 + 转录文字
② 总结      → 人物（带 importance 分层）/ 世界观 / 舞台
③ 外观精修  → 只对 主角 + 主要NPC，各再跑一次「只看外观与服装」的带图请求
```

几个关键设计：

| 决策 | 原因 |
| --- | --- |
| **只精修 主角 / 主要NPC** | 每个角色一次带图请求；路人本来就该略写，全量精修成本翻几倍且焦点跑偏 |
| **分层用总结时标注的 `importance`** | 模型从资料里判得出谁重要；缺字段时退回"前 N 个" |
| **给这个角色"他出现过的图"** | 视觉抽取是逐图做的，`imageIndex` 就是线索 |
| **名字对不上时按页均匀采样** | 视觉模型起的名字（"黑发兽耳少女"）与总结起的名字（"オスガキさん"）常不同，硬跳过等于白做；采样交给模型自己认，认不出它会回 `found:false` |
| **只在更详细时覆盖** | 精修反而更短就保留原描述 |
| **`found:false` 绝不清空** | 宁可保留原来那句，也不能把角色写没 |
| **看不清的部位记进 notes** | 明确写"哪些部位受遮挡/视角限制不可辨"，而不是编造 |

精修 prompt（`STEP_IMAGE_DETAIL`）按要点逐项要求，避免又写成一句概括：

- 外貌：发型（长度/刘海/发尾/发色含渐变）、面部（脸型/眼型/瞳色/眉/唇/痣疤）、肤色体态、特殊标记（兽耳/角/尾巴/纹身/义体）
- 服装：**上装 / 下装 / 外搭 / 鞋袜 / 配饰** 分层写，外加整体风格与配色
- 同样禁止指涉图片本身、禁止写剧情、禁止编造

**代价**：每个主要角色多 1 次带图请求。页面上的「✨ 主要角色外观精修」开关可以关掉；
CLI 用 `--no-refine`，`--detail-max N` 控制精修几个角色。

## 从本机目录直接生成（不用一张张选图）

漫画一话常常几十上百张，一张张点选不现实。所以有两个入口：

**① 网页版**：「图片 → 卡」页的「① 选择图片」下面有一个
**「或：填一个本机图片目录」** 输入框。填绝对路径（如
`F:\漫画\某作品\第1话`），点生成即可，不用选图。

**② 命令行**（适合批量/自动化）：

```powershell
$env:N2C_BASE_URL='https://api.deepseek.com/v1'
$env:N2C_MODEL='deepseek-flash'
$env:N2C_API_KEY='sk-...'          # 只从环境变量读，不写任何文件
node scripts/image-card-from-dir.mjs "F:\漫画\某作品\第1话" --title "第1话"
```

先看不花钱的批次计划：

```powershell
node scripts/image-card-from-dir.mjs "F:\漫画\某作品\第1话" --dry-run
```

两者共用同一个扫描函数 `listImagesInDir`（`src/image_card.js`），所以规则一致：

| 规则 | 说明 |
| --- | --- |
| 扩展名 | 只收 png / jpg / jpeg / webp / gif；txt、json、隐藏文件自动跳过 |
| 页序 | **自然序**（`1,2,10` 而不是 `1,10,2`）—— 页序错了整本剧情就乱 |
| 数量 | 沿用 60 张上限；超了会明确说"目录里 N 张，上限 60" |
| 子目录 | 不递归扫描，但会提示"还有 N 个子目录" |
| 产物独立性 | 图片会**复制进任务目录**，所以之后移动/删除原目录不影响产物复查 |

**安全**：浏览器拿不到目录列表，所以这件事必须由本机服务做。既然服务要读任意目录，
就必须自己把关：**只接受回环地址（127.0.0.1）发起的请求** —— 即使把 `HOST` 设成
`0.0.0.0`，这个入口也只服务本机，不会变成"远程读盘"的口子。

## 最多 60 张，自动分批

上限是 **60 张**。关键是它**不是一次请求塞 60 张** —— 而是按每批 6 张切开、
并发送模型（默认并发 2），再合并结果：

```
20 张图 → 4 批（6/6/6/2）→ 20 条人物档案     实测约 39-44 秒
```

理由：一次塞太多不会超上下文，而且**每张图分到的注意力会被稀释**，
后面的页描述明显变差。每批张数可以在页面上调（1-12）。

几个容易踩的点：

- **「图N」必须是全局编号**。分批后每批的图片下标都从 0 开始，
  直接用会把第 13 张图标成「（图1）」。做法是先按本批夹取越界下标、**再加 offset**
  —— 顺序反了会把后面所有批次夹回 0。
- **跨批要去重**。同一个角色贯穿全书是常态，同名档案会让变量树
  `characters.<varKey(名)>` 塌成一个键（实测 2 个人物只剩 1 个），
  所以合并后按名字再去重一次，用全局图号区分。
- **批次成功但没抽到人物也要报**。实测遇到过 20 张只出 18 条：某批没报错、
  返回了 0 条档案，那两页图就静默消失了。它不是"失败"，所以单独统计并警告。
- **模型说"看不见图"时必须失败**，不能默默产出一张空壳卡。

## 超长截图自动切片（`src/image_slice.js`）

**要解决的问题**（用户报告"较大的图片无法读取文字"）：

一张 `720x6269` 的手机长截图（宽高比 **1:8.7**）原样发给视觉模型时，
**只读到了帖子的小头像，正文一个字没读到**。原因不是"图太大"，
而是**整图被缩放到模型的视觉尺寸上限**：6269px 被压到约 1/5.4，
字号等效于 133px 显示高度，无法辨认。

**做法**：按竖直方向把超长图切成若干片，每片保持接近原分辨率。
上面的例子切成 6 片 `720x1152`，**每一片里的中文都清晰可读**（已人工核对）。

```
720x6269 (1:8.7)  →  6 片 720x1152，重叠 9.6%
1080x991  (1:0.9) →  不切
887x1920  (1:2.2) →  不切（正常手机截图）
```

参数（`SLICE_DEFAULTS`）：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `maxAspect` | 3 | 长边/短边超过这个比例才切 |
| `targetAspect` | 1.6 | 每片的目标宽高比（高/宽），接近常见截图一屏 |
| `overlap` | 0.08 | 相邻片重叠比例，**防止正好切在文字行中间** |
| `maxSliceHeight` | 2600 | 单片高度上限 |
| `maxSlices` | 8 | 一个文件最多切几片 |

关于代价，说清楚：**切片不会让视觉 token 变少**（片间重叠还会略多）。
它是**拿 token 换可读性** —— 每片的可用分辨率与面积比大幅改善，
这才是"能不能读到字"的关键。所以默认只在确实过长时才切。

**切片后必须维护映射**：一个原图对应多个文件，模型按文件顺序报 `imageIndex`，
必须映射回原图下标，否则「（图5）」会指向一张不存在的图
（`normalizeCharacterProfiles` 的 `imagePaths` 参数）。同时 prompt 里要明确
告诉模型"这几段属于同一张图，别重复登记同一个人"，否则同一个人会被登记好几遍。

`sharp` 是**可选依赖**（带平台二进制，装不上时 `npm install` 仍会成功）：
缺失时自动跳过切片并在日志里说明，不会让任务失败。

## 同一张图只留一个角色（切片带来的重复）

切片让**一个原图对应多个文件**，于是出现了新问题：模型为每一段各输出一条档案，
名字依次是「银发头像少女 uyu」「…（图1）」「…（图1）·」…（去重逻辑加的点），
**一个人变成了 6 个角色**。它在变量树里占 6 个键，卡里多出 5 条纯重复条目。

prompt 里已明确要求"同一个人只输出一条、用 sliceIndexes 标明出现在哪几段"，
但**不能只靠 prompt** —— 模型不听时用户就会看到这种结果。所以代码里有一道兜底：
`mergeSameImageProfiles` 按原图分组，把**归一化后同名**的档案合并成一条
（去掉「（图N）」与尾部 `·` 后再比）。

合并判据刻意保守，只说"名字归一化后相同"：

| 情况 | 处理 | 理由 |
| --- | --- | --- |
| 同图、名字只差后缀 | **合并** | 基本可以确定是同一人的多段 |
| 同图、名字不同 | **保持分开** | 可能是同一张图里的两个人，代码不该硬猜 |

这是**有意的取舍**：错误合并会**丢角色**（把两个人并成一个，用户很难发现），
而漏合并只是多一条重复条目（一眼看出、可手动删）。所以宁可漏合。

## 截图里的文字要被真正用起来

聊天记录 / 帖文 / 漫画旁白这类截图的**文字才是主要信息源** ——
之前 prompt 没要求转录，模型只能围着"头像直径只有 60 像素"打转，
卡里的 `description` 也成了「图片未提供；该角色在 6 张截图里没有以任何形式出现…」
（全是"看不见什么"，用户看了不知道这卡里有谁）。

改动：

- prompt 新增 `transcript`（逐段转录画面文字）与 `namesFromText`（文字里的称呼），
  并明确"**文字是画面的一部分，据此填写不算编造**"
- 转录汇总成一条 `system_item` 世界书条目「图中文字（转录）」，
  带 `帖文 / 聊天记录 / 对话 / 原文` 触发词；高度重叠的转录会去重
- `description` 改为「身份 → 关系 → 外貌」的摘要，优先用文字里的信息，
  不再拿"图片未提供"当主体
- `scenario` 优先写**文字里的关系与身份**（"住同一寝室""导员"），
  而不是「这是一张深色模式的手机截图」——后者描述的是截图本身，不是故事场景
