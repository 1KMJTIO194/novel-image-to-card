# 合并调用：同一段正文只喂一次

把调用从「按任务切」改成「按文本块切」——一个文本块只进一次模型，一次返回多个任务的结果，
之后在本地拆开、各走各的既有处理链路。

## 一、动机（实测字符账）

优化前，同一部 30 章小说里同一段正文被反复投喂：

| 文本块 | 被喂几次 | 输入占比 |
| --- | --- | --- |
| 每章正文 | 2 次（时间线 + 事件） | 27% |
| 每批正文 | 4 次（世界观 + 物品 + 人物名单 + 摘要） | 30% |
| 人物抽样 | 每个角色 1 次 | **30%**（15 个角色时最大单块） |

合计输入是正文的 **12.5 倍**。

## 二、做了三件事

| 优化 | 原来 | 现在 | 开关 |
| --- | --- | --- | --- |
| 逐章合并 | `STEP_1_MENTIONS` + `STEP_2_EVENTS` 两次调用 | `STEP_CHAPTER_EXTRACT` 一次返回 `{mentions, events}` | `mergeChapterCalls` |
| 逐批合并 | `STEP_5_WORLDBOOK` + `STEP_5_ITEM` 两次调用 | `STEP_5_WORLDBOOK_ITEMS` 一次返回 `{worldbook, items}` | `mergeWorldCalls` |
| 档案批量 | 每个角色一次调用，各带一份相同抽样 | `STEP_5_CHARACTER_BATCH` 一次写一组（≤6 人） | `mergeCharCalls` / `charBatchSize` |

### 刻意**没有**合并的两处

- **人物名单**：它要带「前文上下文」（已出场人物名 + 事件名），依赖上下文链；
- **分批摘要**：它是下一批上下文的输入，按批顺序传递。

把它们并进逐批调用会让上下文传递链断裂 —— 摘要拿不到该批的结构化结果，
而摘要正是"跨批别名归并"的依据。实测上下文块本身只占输入 **1.02%**，压它没有收益。

## 三、实测收益

`node scripts/compare-merge-usage.mjs`（假 LLM，同一部 30 章 / 3.7 万字 / 10 角色跑两遍）：

```
指标                    拆分（关掉合并）      合并（默认）        变化
------------------------------------------------------------------
请求次数                            90            46      -48.9%
输入字符                       479,567       271,698      -43.3%
输出字符                        18,455        21,089      +14.3%
失败调用                             0             0          —
输入/正文字符                     12.53          7.10      -43.3%

产物：两条路径完全一致（世界书 17 条 / 人物条目 10 / 卡内条目 25 / 变量树人物 9）
```

按 Step 看（合并版）：

```
43.6%   10 次   118,376  step5          （拆分版：59.7% / 24 次 / 286,351）
35.8%   30 次    97,194  step1+step2   （拆分版：step1 16.2% + step2 14.0%，共 61 次）
14.6%    3 次    39,548  step-batch    （未动）
```

**人物档案那一块降得最狠**：10 次 112,539 → 2 次 23,691 字符（-79%）。

## 四、踩过的坑

### 1. 合并 prompt 里不能偷懒删规则

合并省的是**重复的正文**，不是要求本身。三个合并 prompt 的规则部分是逐字照抄单任务版的，
`tests/pipeline-merge.mjs` 锁住了每条关键规则片段（`scope 规则`、`pressure 三条件`、
`与主线关联`、`私钥细节描写`…）。删掉它们不会报错、产出还是合法 JSON，
只是内容变差 —— 最容易悄悄退化的就是这种。

### 2. 两个数组不能用 `asArray` 取

合并返回 `{worldbook:[...], items:[...]}`，而 `asArray` 的兜底是"对象里第一个数组值"——
取 worldbook 时可能拿到 items，**而且静默**（条目数看着正常，分类全错）。
新增 `pickArrayByKeys(raw, keys)`：只认给定的键，拿不到就返回空，绝不猜。

### 3. 预设的 step 级后缀会丢

预设在**每个 Step 上可配置后缀**（append/replace）。合并调用原先只带一个 step 名，
另一个 Step 的配置就静默失效了。

修法：`stepName` 允许传**数组**（`['step1','step2']`），`resolveSuffix` 按顺序逐个追加，
global 只加一次。用量记账把数组合成 `step1+step2`，一笔开销不拆成两行。

### 4. 假 LLM 的 mock 键名会静默让优化失效

批量档案的 prompt 开头也是"你是人物档案抽取器"，用这个短键做 mock 匹配，
会让**单任务版应答命中合并版请求** → 返回单角色对象 → 每个角色都判为"缺失" →
退化成逐个补抽。表面上跑得通，实际优化完全没生效（第一次对比就踩了：
合并版 12 次调用 > 拆分版 10 次）。

教训：mock 键要用能区分两种 prompt 的**短语**，且合并版键要在前。

### 5. 批量不牺牲单角色的详细度

字段模板与单角色版逐字一致，prompt 里明确要求"不能因为一次写多个就写短"、
"某个角色信息少时按实际写，**不要用别的角色的信息填充**"。
批量拿不到/拿成占位的角色会**逐个补抽**，不整组失败。

## 五、可回退

三个开关默认全开，都能单独关掉：

```js
runPipeline({ ..., mergeChapterCalls: false, mergeWorldCalls: false, mergeCharCalls: false, charBatchSize: 1 })
```

设置页与生成页的「高级参数」也有对应勾选框。

**为什么必须保留回退**：合并后的质量只能在真实长篇上验证。假 LLM 能证明
"字符数降了、产物结构一致"，**证明不了**"一次抽多类"不比"分多次抽"差。
真实使用中发现某一步产出变差时，单独关掉那一个开关即可定位。

## 六、验证方式

| 位置 | 内容 |
| --- | --- |
| `tests/pipeline-merge.mjs` | 合并 prompt 的关键规则片段、对象形态要求（16 项） |
| `scripts/compare-merge-usage.mjs` | 跑两遍对比用量 + **回退路径回归**（11 项断言：两条路径都跑通、产物一致、合并确实更省） |
| `tests/e2e.mjs` | 真实 HTTP 链路走合并路径（含预设后缀、分层、产物结构） |
| `meta.json` → `usage` | 每次生成都记录输入/输出字符、按 Step 汇总、`inputPerNovelChar` |

## 七、未能验证的

- **真实模型上的质量**：全部用假 LLM。合并后单次输出更长，真实模型可能
  在"一次写 6 份档案"时对靠后的角色写得更潦草 —— 这需要真实长篇对比才能判断。
  产出里已有 `Step 5` 的"档案偏短"告警（`<400 字`），可以用它做初步筛查。
- **Prompt Caching 的收益**：`llm.js` 只按字符记账，不读上游 `usage`。
  而且能缓存的前缀只有约 1.1k 字符的系统提示，真正的大头是随调用变化的章正文与抽样 ——
  缓存不到。没做。
- **实际费用**：字符数 ≈ token 的粗略换算（中文约 0.7），不是精确计费。
