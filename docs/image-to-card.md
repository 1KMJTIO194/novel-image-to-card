# 图片 → 角色卡

新增功能：上传若干张人物图 → 生成与「小说 → 角色卡」**结构完全一致**的角色卡。
入口在侧边栏「工作台」组的**生成流程下方**（`#/image-card`）。

## 与小说路径的关系

```
小说路径： 文本 → 切章 → 每批抽取 → 归并 → 人物/事件/世界观 → 变量树 → 状态栏 → 卡
图片路径： 图片 → 视觉抽取 ────────────────────────────────→ 人物档案 ──┘
```

后半段**完全共用**：同一套 `buildVariables` / `generateStatusbar` / `assembleCharacterCard`，
所以产出的卡在酒馆里的用法与小说路径一致，产物目录结构也一致
（`character_card.json` / `worldbook.json` / `statusbar_preview.html` …），
「任务与产物」页、下载、打包全都直接复用。

## 一、给 `llm.js` 加多模态

这是唯一的基础设施缺口 —— 原来 `content` 是纯字符串。

```js
const reply = await llm.chat(system, user, 'image-vision', {
  images: ['a.png', 'b.jpg'],   // 路径 / data URL / {data,mime}
});
```

三个实测得到的硬约束，都写进了注释：

1. **必须用对象形式**：`image_url: { url }` 而不是 `image_url: 'data:...'`。
   字符串形式会被网关 422 拒绝（`invalid type: string`），而且错误信息不会指出是写法问题。
2. **格式只认 webp/png/jpeg/gif**。上游报错不会说是**哪一张**，所以
   `validateImages()` 在调用前就点名"图片3 格式不支持（.bmp）"。
3. **图片要计入记账**。我们按字符数记账，而图片没有字符 ——
   不计进去视觉任务的成本会算成 0。每张图折算 1500 字符（按实测 prompt_tokens 反推）。

## 二、最要紧的一道闸：识别"模型其实没看图"

这是本功能**最容易出错**的地方，值得单独说。

实测 `api.deepseek.com` 的 `deepseek-flash` 直接报 400；
`deepseek-v4-pro` 接受图片字段、返回 200，但内容说"我无法查看这张图片"。

**更危险的是**：它还会返回**结构完全正确的 JSON**，只是每个字段都写成

```
appearance: "由于图片未能加载或格式不支持，无法获取任何视觉信息，
             因此无法辨认角色的发色发型、瞳色眼型、肤色、面部特征…"
```

如果不拦，用户会拿到一张**看起来正常、实际一个字有用信息都没有的空壳卡**。
这比直接报错危险得多。

### 判据的演进（三次踩坑）

| 尝试 | 结果 |
| --- | --- |
| ① 匹配拒绝词（"无法查看"） | **漏判** —— 它写的是"图片未提供或无法解析""输入图片缺失" |
| ② 判断有没有具体名词 | **漏判** —— 拒绝文本里本身就有"发色/瞳色/肤色"这些具体词，只是在否定语境里 |
| ③ 剥掉拒绝措辞后看剩多少字 | 阈值 30 **误伤**简短但真实的答案；阈值 8 又漏掉拒绝文本 |
| ④ 按子句切分、否定子句整句不计 | 仍然分不干净：拒绝文本 8-9 个具体词 vs 简短真实 2 个，**计数完全重叠** |

### 最终方案：让模型自己声明

prompt 要求它**先回答 `sawImage`**（true/false）。这比任何后验启发式都准。

- `sawImage === false` → **直接判失败**，并把模型自己给的原因透出来：
  ```
  模型 deepseek-v4-pro 没有给出可用的视觉分析（模型自述没能看到图片（sawImage=false）；
  模型自述的原因：图片未能加载或格式不支持，无法看到画面内容）。
  当前端点/模型不具备图片理解能力。请换用支持视觉的模型（如 gpt-4o、gemini、qwen-vl、ollama+llava 等）
  ```
- 漏答 `sawImage` → 走内容兜底，**放行但标记 `verified: false`**，
  并在进度日志与 README 里显式写：
  > ⚠️ 图片可见性未经验证：模型没有回答"是否看到图片"。请自行核对内容是否与图片相符。

**这个取舍是刻意的**：兜底分不干净，误放行一张信息不全的卡（用户能看出来）
比误判失败（用户以为功能坏了）代价小 —— 但必须**告诉用户没验证成**。

## 三、诚实性：图片给不了的东西不编

小说路径有原文可依；图片路径**没有**。所以：

- **描述性字段只写看得见的**（外貌/服饰/体型/场景）
- **推断内容单独放 `inferred*` 字段**，正文里一律标注「（据画面推断）」
- 看不到的写「图片未提供」，**绝不用占位文本凑满**

```yaml
appearance: |
  银色长发垂至腰际，赤色瞳孔，皮肤白皙        ← 看得见的
clothing: |
  黑色皮衣，金属铆钉
background: |
  可能是佣兵（据画面推断）                    ← 推断，明确标注
personality: |
  图片未提供（外貌无法可靠推断性格，需用户补充）  ← 不编
```

测试里有一条专门断言：**描述性字段区里不能出现推断内容**。

另外，图片没有剧情，所以事件表只造一条「开场」占位，
并在 README 与开场白里说明"需要你自己推进"，而不是编一段假剧情。

## 四、用户模式固定为 `participant`

踩过的坑：一开始照小说路径默认 `protagonist`，于是 `initializeUserNamespace`
**把第一张图的角色从 `characters` 移进了 `user`** —— 而这个角色的档案就只剩
`user.name` 一句名字，外貌/服饰被埋掉，状态栏也少一页。

图片路径里"第一张图的角色"就是**图里的人物**，不是用户化身。
用户是**看着这些图的人**，所以 `participant` 才是对的：所有图片角色都留在 `characters`。

## 六、视觉能力：实测结论与一次自我更正

> ⚠️ **本节修正过一个错误结论。** 我最初报告"这个端点看不了图"，
> 那是**用错误方式测出来的**，结论是错的。下面是重测后的正确结果。

### 正确结论：`deepseek-flash` 能看图

| 图片 | `deepseek-flash` 的回答 |
| --- | --- |
| 64×64 纯红 PNG | "这张图是一个纯红色的正方形。" |
| 512px 真实照片 | "夜晚霓虹灯下的城市街道景象，潮湿路面反射着黄色斑马线和店铺灯光，远处有高架结构、发光招牌与零星行人剪影。" |
| 1024px 真实照片 | "赛博朋克风格的未来城市街道夜景，潮湿路面映着霓虹灯光，有黄色斑马线、悬挂招牌、高架结构和零星星行人。" |

描述**相当准确** —— 潮湿路面反光、黄色斑马线、霓虹招牌、高架、行人剪影全都对得上。

### 我之前错在哪

1. **拿 1×1 像素的退化图当探针**。那次 `deepseek-flash` 报
   `HTTP 400 unsupported image`，我据此推断"模型不支持视觉"——
   实际那是**图本身无效**，不是模型不支持。
2. **把 `deepseek-v4-pro` 的行为安到了 `deepseek-flash` 头上**。
   实测**真正"看不见"的是 `deepseek-v4-pro`**：真实图片下 `finish_reason: length`、
   `content` 为空。而它是个**推理模型**，我用的 `max_tokens`（300/800）被思考 token 吃光，
   正文一个字都没输出，于是它回"无法查看图片"。
   这和项目里早先踩过的**批次摘要 `maxTokens: 800`** 是同一个坑。

教训：探针数据必须**有效**（1×1 像素的图会被上游拒绝），
而且**不同模型要分别测**，不能把一个模型的表现当成端点的表现。

### 正确用法

```
模型：deepseek-flash        ← 用这个
```

`deepseek-v4-pro` 除非给足 `max_tokens`（推理预算），否则视觉任务会因截断而失败。

### 端到端实测（`deepseek-flash` + 一张赛博朋克街景照）

```
[Vision]     视觉抽取：1 张图 + 用户文字设定
[Assemble]   角色 1 人 / 世界书 2 条 / 状态栏主题 scifi / 14 条条目
[done]       ok
```

产出的档案把画面里能看到的都写了，**看不清的也如实说看不清**：

```yaml
name: 左侧人行道暗影行人
confidence: low                       ← 人物是背光剪影，如实标低
appearance: |
  因人物在画面中仅占极小面积且处于背光暗部，整个身体呈几乎纯黑的剪影，
  无法辨认发色、发型、瞳色、眼型、肤色或任何面部特征…
clothing: |
  仅能从外轮廓看出一件较为宽松、下摆垂到大腿附近的深色上身外衣，
  下身轮廓略窄，似为长裤或紧身下装；是否穿着外套、是否有图案或反光条一概无法确认。
scene: |
  夜间城市街道，正中央是一条宽阔的沥青马路，路面湿润反光，横贯一条醒目的黄色斑马线；
  两侧是低层沿街商铺与卷帘门，左边墙面有大面积涂鸦，右边挂着发光招牌与品红色霓虹灯带…
```

**主题识别正确**：`worldHints` 含"赛博朋克"→ 状态栏主题自动选 `scifi`。

### 关于"看不见图"那道闸

上面那套闸门逻辑（`sawImage` + 内容兜底）**依然必要** ——
换成 `deepseek-v4-pro` 或任何纯文本模型时，它正是用来防止静默产出空壳卡的。
只是它不再是"当前默认配置下的常态"，而是**兜底**。

## 七、真机跑通后修掉的三个问题

用 `deepseek-flash` + 真实照片跑通后，暴露出三个只有真数据才能发现的问题。

### ① 世界书条目名成了一整段场景描写

视觉模型给的 `scene` 是一整段描写（100+ 字），我原来**直接拿它当条目名**：

```
[map_location] 夜晚的城市街道，两侧为低层商铺与带招牌的楼房，路面上有醒目的黄色斑马线，
               头顶是巨大的混凝土立交或高架结构，远处路灯与霓虹招牌在湿滑沥青路面上投出反光…
```

条目名和**触发词**都变成了那段话。修法：`shortPlaceName()` 取第一个子句并限长 14 字
→ `城市街道`；**完整描写仍保留在条目正文里**，信息不丢。

### ② "与上一张为同一处"被当成了新地点

模型对第二张图会说「**与上一张为同一处**夜晚街景：高架混凝土巨构横跨头顶…」——
那是在声明"同一个地方"，我却照单收下，于是世界书里多出一条名字叫
「与上一张为同一处夜间城市街道」的条目，触发词也是那句话。

修法：识别 `与上一张／与前景／同一处／同上` 这类指回表述，**直接跳过**，不生成地点条目。

### ③ 同名角色让变量树互相覆盖（最严重）

两张图是同一场景里的两个剪影，模型给了**同一个名字**（都叫「左前景剪影行人」）。
而变量树是 `characters.<varKey(名)>`，**同名直接塌成一个键**：

```
模型返回 2 个角色 → 变量树 characters 只剩 ["左前景剪影行人"]   ← 丢了一个
```

后果：状态栏少一页、AI 永远更新不到第二个角色。

修法：`normalizeCharacterProfiles()` 里做**名字去重**，重复的加「（图N）」：

```
夜街暗影行人（左）
夜街暗影行人（左）（图2）
```

不去猜"到底是不是同一个人" —— 那是视觉判断，不该由代码硬猜；
名字不同至少卡是完整的，用户可以自己合并。

### 修完的最终产出（2 张图）

```
[Vision]    视觉抽取：2 张图
[Assemble]  角色 2 人 / 世界书 2 条 / 状态栏主题 scifi / 15 条条目

人物：夜街暗影行人（左） / 夜街暗影行人（左）（图2）      ← 名字不同
变量树：["夜街暗影行人（左）", "夜街暗影行人（左）（图2）"]  ← 两个键都在
世界书：[map_world] 两张图测试 | [map_location] 未来都市街道  ← 只有 1 条地点
完整卡：15 条条目 / 7 条正则
```
