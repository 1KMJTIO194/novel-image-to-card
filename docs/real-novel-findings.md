# 真实小说跑一遍发现的三个 bug

用一篇真实小说（23,403 字 / 90 行 / UTF-8 / 成人向）完整跑过之后，
暴露出 3 个**测试数据永远碰不到**的问题。全部已修，并用真实模型验证。

## 测试数据为什么碰不到

我的测试数据都是几百字的短章、每章一行、没有书名行。真实文本的特征完全不同：

```
文件 69,955 字节 / 23,403 字 / 90 行
第 1 行是**文件名**（39 字，含 # 标签）
第 2 行是**概括性的开篇简介**（整篇正文挤在极少数行里）
整篇只有 2 个真章节标记：第16章（@13594）、第17章（@15628）
```

前 13,594 字（58% 篇幅）**没有任何章节标记**。

---

## Bug ①：`chunkMaxLen` 完全失效

```js
// src/utils.js 原实现
if (parts.length > 1) {
  return parts.map((p, i) => ({ index: i, title: titleOf(p, i), text: p.trim() }));
}
// ← 直接返回，maxLen 连看都没看
```

只要文本里有 2 个以上章节标记，超长章节就原样放行。实测三档设置结果**完全一样**：

```
chunkMaxLen=6000/3000/1500 → 都是 2 块：15,630 字 + 7,773 字
```

连锁后果：

| 后果 | 实测 |
| --- | --- |
| 章序全错 | `第16章` 标记在第 13,594 字处，它前面 58% 的正文也被归进「第16章」 |
| 分批失效 | 23,403 字只算 1 批 |
| 提及塌陷 | 提及按章聚合，只剩 2 条 |
| 第一块标题是文件名 | `示例小说 B 开局签到无敌全城围观…` |

### 修法

`splitLongPart()`：超长章节按**段落边界**（空行 → 单换行 → 硬切）切成 ≤ maxLen 的多块。

三个要点：

1. **续块带限长前言**（本章第一句正文）—— 既是内容上下文，也天然成为标题。
   否则续块标题只能编成「（续 2/4）」这种没信息量的东西。
2. **封面/文件名行要跳过**。实测第 1 行是文件名（短、无句读、带 `#`），
   若不跳过，每个续块的前言都是这个文件名。
3. **标题必须块块唯一**（见 Bug ①b）。

## Bug ①b：续块标题重复 → 章序映射塌陷

修完 ① 之后出现一个新回归：同一章的多个续块，前言取自**同一句**，标题完全相同。

```
chapterTitles: ["示例世界第三章，","示例世界第三章，","示例世界第三章，","第17章，","第17章，"]
```

而 `solveTimeline` 用 `Map<标题, 章序>` 建索引、**同名只留第一个** ——
5 个块塌成 2 个章序，时间线锚定错乱（实测把时间线条目清成了 **0 条**）。

修法：续块标题加位置标记 → `【2/3】示例世界第三章，`。既唯一，也能一眼看出是第几段。

## Bug ②：批次摘要的 `maxTokens: 800` 必然失败

```js
llm.chatJSON(S.STEP_BATCH_SUMMARY, …, 'step-batch', { maxTokens: 800 })
```

这是**全项目唯一**设了 `maxTokens` 的地方，而推理模型的思考也计入 completion。实测：

```
finish_reason: "length"
completion_tokens: 800
completion_tokens_details: { "reasoning_tokens": 800 }   ← 全用在思考
content: ""                                              ← 正文一个字没写
```

于是 `JSON.parse('')` 必然抛错，批次摘要**每次都是空**，静默退回确定性摘要；
同时白烧一次整批正文的输入（实测占全部输入的 **11.8%**）。
多批长篇里还会失去"前情摘要"的传递。

修法：去掉上限，由模型自己收尾（prompt 本来就要求"简短摘要"）。

**修后验证（真实调用）**：

```
finish_reason: stop
completion_tokens: 2339 / reasoning: 2083
✓ JSON 解析成功，键: summary, phase, newCharacters
  summary 285 字
```

**第二本小说的三批也都成功了**（《示例小说 A》21 章 / 3 批）：

```
[Step 1] 批次 1/3 摘要：358 字，阶段「陨落重生」，新人物 7 人
[Step 1] 批次 2/3 摘要：352 字，阶段「入门修炼」，新人物 6 人
[Step 1] 批次 3/3 摘要：256 字，阶段「求道谷觅宝」，新人物 1 人
```

修复前这三批**必然全部为空**（`finish_reason: length` + `content: ""`），
而且每批白烧一次整批正文的输入。

## Bug ③：批量档案在推理模型上退化

实测一次要 11,400 输出 token（其中 **7,300 是思考**）才能写完 5 份档案。
pipeline 那次只吐回 1 份就结束，剩 4 人走逐个补抽 —— 批量调用白花、成本反而更高。

```
[WARN] 批量档案里缺「刘晓月」（模型返回 1 份），将单独补抽
[Step 5] 档案组 2/2：1/5 人
[Step 5] 4 人需要单独补抽
```

修法：**首组自适应**。先跑第一组，若返回比例 < 60% 就自动把后续批次降一档并重分组，
同时把首组结果复用、不重跑。开关 `reduceCharBatchSize`（默认开）。

**修后验证**：

```
[Step 5] 档案首组 6/6 人（100%）
[Step 5] 档案组 2/2：5/5 人
人物 11 份，平均 1034 字（字段数 15-15）
```

—— 没有再出现补抽。

## 顺带：钟点不是日期

这次小说只有相对时间（`四点了`），`parseDateParts` 不认钟点，
于是 `worldDate` 把「四点」当成了日期。现在单独给 `timeOfDay` 字段：
有日历成分时不掺进来；只有钟点时作为退路输出（总比显示「未知」强）。

## 仍未解决：时间线只有 1 条

结果里 `timeline.events = 1`，但那不是代码 bug —— 这次模型抽出的 **74 条提及里
51 条是 `relative`、只有 1 条 `absolute`**，而 `solveTimeline` 只收 `absolute` 进事件时间线。

**这是个真实的设计缺口**：文本只有相对时间时（「前两天」「四点了」），
事件时间线会被清空，连带：

- `worldDate` 只剩「四点」
- 事件的 `dateKey` 全为空 → 按天打包失效
- 阶段取文（依赖事件）失去依据

值得单独做一轮：把 `relative` 提及链到锚点事件上（solveTimeline 已有相对推算逻辑，
但入口被 `absolute` 拦住了）。**这一轮没做**，因为改动面涉及时间线语义，需要单独验证。
