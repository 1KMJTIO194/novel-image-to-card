# 时间线的构成方式（第二轮真实小说修复）

接 `real-novel-findings.md`。上一轮末尾留下的"时间线只有 1 条"那个缺口，这一轮做了。

## 根因：时间线是用「时间提及的事件名」拼的，不是用「剧情事件」拼的

```js
// solveTimeline 里收集时间线的那一段
for (const m of ms) {
  if (m.type !== 'absolute' || !m.event) continue;   // ← 只认 absolute
  put(..., { name: m.event, time: m.raw, ... });
}
```

两个问题叠在一起：

**① 只认 `absolute`。** 实测一篇小说 77 条提及里 **57 条是 `relative`**（`今天`／`第二天`／`四点了`），
全被这一个条件过滤掉，只剩 1 条 absolute 进时间线。

**② 按事件名去重**（`put` 同名只留首见），而 `m.event` 是抽取器给"时间提及"起的名字，
与 Step 2 的剧情事件名**不是同一套**。所以时间线条目是 `四点了`／`今天` 这样的时间短语。

后果：世界书的时间线只有 1～2 行、`worldDate` 变成「四点了」、
事件的 `dateKey` 全空 → **按天打包完全失效**、阶段取文失去依据。

## 修法：时间线由剧情事件构成

`solveTimeline` 新增 `displayEvents` 参数。调用方把 **Step 2 的剧情事件**传进来，
它仍然负责排序、解析日期、挑 `worldDate`。

**顺序上有两处讲究**：

1. **必须先 `backfillEventTimes` 再解时间线**（否则事件带不上日期）。
   回填因此从 Step 8 前移到了时间线之前。
2. **`null` 与 `[]` 语义必须不同**：`Array.isArray` 判定 ——
   空数组表示"调用方明确给了事件清单，只是它是空的"，不能静默退回旧行为
   （拿时间提及拼时间线），否则调用方以为传了空清单、实际拿到一堆时间短语。

效果（同一篇小说）：

```
改前：时间线 1 条（一个时间短语）
改后：时间线 24 条（= 剧情事件），其中 14 条带上了时间
```

## 顺带修掉的两个 bug

### Bug A：章节号形式不同导致回填全军覆没

事件的 `chapter` 由模型写（`示例世界第三章`／`2/3`／`16`），
而时间提及的 `chapter` 是块标题（`示例世界第三章，`／`【2/3】示例世界第三章，`）——
**两者形式不同**，精确查表必然落空。

于是每个事件都落到兜底，**实测 17 个事件全被标成同一时刻（全变成「四点了」）**。

修法：章节号的**模糊匹配** —— 去掉标点与 `【】` 标记后互相包含即视为同一章。

```js
const normChapter = (s) => s.replace(/[【】\[\]（），,。.、：:；;！!？?\s]/g, '');
// 归一化后：'2/3' 与 '2/3示例世界第三章' 互为子串 → 同一章
```

### Bug B：兜底把"第一个时间点"当成所有事件的时间

```js
if (!hit && free.length) hit = free[0];          // 同章内按顺序分配（合理）
if (!hit && chapterMentions.length) hit = chapterMentions[0];
// 加上最后的 startTime 兜底 —— 对不上章的事件也会被塞上故事起点时间
```

给错的时间比留空更糟：它会让 AI 以为整篇都发生在同一刻。

修法两条约束：

- **事件自己带了章节号、但该章一个时间点都没有** → 不兜底，留空
  （序列化成 `时间：（未定）`，是诚实的）
- 全局唯一候选的兜底**用掉就不再复用**

## 加了一条诊断：时间线稀疏时说明原因

判据是**"有时间的条目占比"**，不是条目总数 —— 一开始按总数判，
于是「15 个事件里只有 1 个拿到时间」这种情况**反而不告警**（总数看着不少）。

```
[Step 1] 时间线偏稀疏：24 个事件里只有 1 个带上了时间（61 条时间提及中可定位的时间点太少）。
         通常是模型把时间都判成了"相对/模糊"（如「今天」「四点了」）——
         可换更强的模型，或检查原文是否本来就缺少年月日
```

这条日志是这一轮最有价值的东西：它把"为什么全是（未定）"直接说清了，
而在此之前只能靠一行行加诊断日志去猜。

## 仍未解决（数据层面，不是代码）

**抽取器几乎不产出 `absolute` 提及。** 实测 61 条提及里只有 3 条 absolute，
且都挂在同一个事件名下。这是模型对"相对时间叙事"的提取口径问题。

代码侧已经做到位了：能匹配的都匹配上、匹配不上的诚实留空、并给出可读原因。
但要真正让这类文本拥有可用的日期表，需要改 `STEP_1_MENTIONS` 的口径
（比如允许把 `今天`／`第二天` 归一化成相对锚点链），那是另一个改动，需要单独验证。

## 环境

- `tests/` 下累积了一批 `_tmp-*.mjs` 临时诊断脚本，**本项目内删不掉**。
  用 `diagnose-windows-sandbox-acl` 技能查过一次，结果是清晰的：

  | 对象 | 状态 |
  | --- | --- |
  | `D:\角色卡生成器\tests` | 已修复（补上当前用户完全控制，验证通过） |
  | `tests\_tmp-*.mjs`（文件本身） | **缺少沙箱所需的安全标签**，脚本拒绝修，`GRANTED=0` |

  所以这些文件在会话内无法删除，但完全无害：`npm test` 不引用它们。

  **你在资源管理器里直接删即可**，或打开一个普通 PowerShell 窗口运行：

  ```powershell
  Remove-Item 'D:\角色卡生成器\tests\_tmp-*.mjs' -Force
  ```

- `acl-recovery/` 是那次权限修复留下的备份目录（含回滚脚本与控制台记录）。
  它已被 `.gitignore` 排除（里面有本机 SID 与绝对路径，不适合提交）。
  **在本机不要删** —— 需要还原 `tests/` 的原始权限时要用它。回滚命令形式：

  ```powershell
  pwsh -NoProfile -File '<acl-recovery>\acl-backup-<id>.json.ps1' `
    -Path '<项目>\tests' -AllowRoot '<项目>' `
    -Restore '<acl-recovery>\acl-backup-<id>.json'
  ```

- 真实产出：`output/_tmp-novel-run/task`（改前）、`task2`（改后）
