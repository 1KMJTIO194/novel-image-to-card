# 分批评析 · 实现说明

长篇（>30 章）原来整本一次性处理，有三个问题：
① 单次 LLM 上下文塞不下，抽取质量断崖下降；
② 中途一次失败，前面所有抽取结果全废（没有任何落盘）；
③ 用户看不到"还要多久"。

分批评析把 Step 1/2/5 的抽取按批拆开、逐批落盘、逐批给进度，任何一批失败或暂停都不影响已完成的批次。

---

## 一、批次怎么切

`src/batcher.js` → `splitIntoBatches(chapters, { chapters, chars })`

- 默认**每 10 章或每 3 万字**，**先到者为准**，都可在设置里改。
- **章节不可拆分**：批次边界永远落在章与章之间。一章被劈成两半，Step 2 会从一个句子中间开始读。
- **单章超过字数上限时独占一批**并记 warning，不硬切 —— 硬切破坏句意边界，抽取质量反而更差。
- **`chapter.title` 原样保留**。`solveTimeline` 靠 `chunks.map(c => c.title)` 把时间提及映射回章序，
  归并时也靠标题对齐时间线；重命名会让整条时间线错位。

## 二、执行顺序

```text
Step 0 / 0.5   读入、切块、user 角色定位（全书一次）
── 批次切分 ──
每批循环：
  Step 1  时间提及（批内逐章）
  Step 2  事件（批内逐章）
  Step 5  世界观 / 物品 / 人物名单（按批取样）
  落盘 batches/batch_NNN.json
  生成摘要 → 传给下一批
── 全局归并（Step 2.5）──
Step 1  原点识别 + 时间线求解（全书一次）
Step 3/4  阶段划分、人设增量（全书一次）
Step 5  人物档案（按归并后的全局名单逐个生成）
Step 6/7/7.5/8  变量树、组装、状态栏（全书一次）
```

### 为什么 Step 3/4 没有按批跑（与原需求的偏差）

原需求写的是"Step 1-5 改为按批执行"。实现时把 **Step 3/4 保留为全书一次**，理由：

- **Step 3（阶段划分）分批必然出错**。它的输入是事件序列，输出是 `{startEvent, endEvent}`。
  分批各划一次的话，每批都会把自己范围内的首尾事件当阶段边界 → 跨批的故事弧被切断 →
  阶段数翻倍。而阶段名会写进「角色阶段」条目的 EJS 增量表，变量树里的 `world.phase`
  必须命中那张表，错位就是**静默失效**（EJS 什么都不输出，也不报错）。
- **Step 4（人设增量）依赖 Step 3 的阶段**，阶段错了它跟着错。
- 这两步的**输入很小**（Step 3 只收事件名/压力/简述，Step 4 按阶段取文），
  不存在上下文压力，分批没有收益。

Step 5 则确实按批跑了，而且**质量比原来更好**：原来是对全文做一次分层采样
（`sampleAcrossText` 只覆盖 6-7 个窗口，长篇后半本大量段落从未被看过），
现在每批都过一遍，覆盖面从"6 个窗口"变成"每一段原文"。

人物档案仍按**归并后的全局名单**逐个生成：它的输入是抽样原文 + 一个角色名，
不是"某批的文本"，按批拆只会让同一个人被抽多次。

## 三、摘要链

每批结束后调一次 `STEP_BATCH_SUMMARY`，产出一段 150-300 字摘要 + 本批阶段名。

**摘要链断裂的兜底有三层**（`createContextChain`）：

1. 摘要生成本身失败 → 记 warning，**沿用上一批的摘要**，链条不会突然空白。
2. 摘要为空/纯空白 → 同上，不覆盖。
3. 完全不依赖摘要：`buildDigest` 从**已落盘的抽取结果**算出确定性摘要 ——
   已出场人物名+别名、已抽取事件名、当前阶段。这部分永远算得出来。

确定性摘要的作用不是"讲故事"，而是给后面的批次三样最容易搞错的东西：
**已经出场的人物名与别名**、**已经抽到的事件名**、**时间线推进到哪了**。
把名字先喂过去，能大幅减少"同一个人被不同批次抽出不同名字"的情况 ——
那是全局归并里最难处理的一类。

上下文是**只增不减**的累积器：第 N 批能看到前 N-1 批的**全部**名字，而不只是紧邻的上一批
（长篇里人物可能隔十几章再出场）。

## 四、全局归并

`src/merge_batches.js`。两条不可动摇的规则：

1. **绝不编造**。只做"同一实体的不同称呼"合并，不新增实体，不做语义推断
   （不会因为"两人都在云京"就合并）。
2. **级联保护**。别名必须能被认领，且一个名字只能被一个实体认领。

### 别名归并的两个坑

**坑 1：别名认领顺序不能依赖遍历顺序。**
改成两阶段：先把**所有主名**登记进 `owner`，再让别名去认领 ——
主名永远优先，别名不能反过来把另一条记录的主名吞掉。

**坑 2：主名优选的判据有优先级，`||` 的短路会吃掉后面的判据。**

```js
// 错误的写法（踩过）：
(Number(aliasOnly(b)) - Number(aliasOnly(a)))   // -1 一旦有值就短路
  || (rank(a) - rank(b))                        // 角色等级永远不参与
```
结果是：主名「林昭(主角)」+ 别名「阿昭」，而另一批把「阿昭(主要配角)」当主名时，
**「阿昭」反而赢了** —— 输出里出现了一个只在别名表里存在的名字。

正确顺序（等级 > 是不是别名 > 名字长度）：
```js
(rank(a) - rank(b))
  || (Number(aliasOnly(b)) - Number(aliasOnly(a)))
  || (b.name.length - a.name.length)
```

**刻意不做的合并**：主名互为子串。中文里「林昭」与「林昭仪」是两个人，
子串合并会把整张卡的人搞乱。子串关系只用于**提示**（写进 `merge_report.json` 的 `suspicious`）。

### 事件去重与近似检测

同名合并复用 `dedupeEvents`（保压力高者、合 interventions）。
名字相近的**只报告不合并** —— 事件名是变量键的一部分，错误合并会让导演指令指向不存在的事件。

近似判据刻意都是**结构性**的，不用编辑距离（中文事件名只有 4-6 字，
编辑距离阈值放到 1 会把「夜探旧宅」和「夜探密道」也报出来）：
词干相同（去「之变/事变/之战/之乱/事件/风波」后缀）、互为前缀后缀、去间隔号后相同。

### 时间线对齐

归并后调一次 `solveTimeline(mentions, origin, 全部章节标题)`。
各批的 `chapter.title` 就是全局标题，所以 `title → 章序` 的映射天然正确。

`merge_report.orphanChapters` 是这条链路的守卫：非空说明"有提及的章节号不在章节表里"，
时间线会因此错位。正常情况恒为空数组。

## 五、断点续跑

批次落在 `output/<taskId>/batches/batch_NNN.json`，判"完成"的条件是
**文件存在 + `complete: true` + 每个章节都在 `doneChapterTitles` 里**。
写到一半被 kill 的文件会被判为未完成并重跑；跑到第 7 章中断的批次只重跑第 7 章往上。

**续跑必须复用原 task 目录**，因为批次就在那儿。所以 `resumeTaskId` 同时承担两个作用：
指定 taskId（沿用旧目录）、开关 `config.resumeBatches`。服务端会校验该目录确实有 `batches/`。

前端入口在两处：任务库的「⏯ 继续未完成（2/3 批）」按钮（跳 `/generate?resume=<taskId>`），
以及生成页顶部的续跑横幅（显式说明复用哪个任务、已完成几批，并给「不续跑」出口）。
**不做静默续跑**：复用批次意味着"这一次不会重跑那些章节"，用户必须知道自己拿到的不是全新结果。

## 六、暂停 / 中止

- **暂停**语义是"在下一个批次边界停下"，不是立刻中断：正在飞的那几个 LLM 请求会跑完
  （否则已经花掉的 token 白费）。实现上 `checkAbort()` 顺带轮询 `config.isPaused()`，
  pipeline 抛 `checkpoint` 事件 → server 转成 `PausedError` → SSE 发 `paused`。
- 暂停期间进程不会卡在一个永不 resolve 的 Promise 上：用 400ms 轮询而不是事件等待，
  所以"暂停 → 关页面 → 关服务"都不会留下悬挂的句柄。
- **中止**（cancel）会清掉暂停标志再 abort —— 否则被暂停的任务卡在轮询里，
  abort 后要走完一轮才看得到。
- 群聊场景不受影响：这套只作用于生成端。

## 七、SSE 事件与前端

新增两类事件：

```text
batch  { phase:'start'|'done', index, total, chapters, chars, tokens,
         mentions?, events?, characters?, worldbook?, summaryChars?, elapsedMs? }
paused { message }
```

前端 `active-run.js`：

- `derive()` 新增 `batch` / `paused` / `pausing`。
- 生成页显示「批次 N / 总批数 + 本批章数字数 + 本批进度条」，按钮组加「⏸ 暂停 / ▶ 继续」。
- 任务库详情页显示分批进度卡，并提供续跑入口。

### 进度条的一个非显然坑

批次进度**不能**只映射 `Step 1 → Step 2`（28%）。分批阶段是长篇里最耗时的一段
（每批 4 次 LLM 调用），而 pipeline 会在批次之间穿插打 Step 2/3/4 的日志，
**任何一条都会把步骤进度一下推过去 28%**，批次值就永远追不上，进度条整段卡死不动。

现在的映射是把批次铺满 `Step 1 的 28% → Step 5 的 82%`，并且最终取
`max(步骤进度, 批次进度)`：既不会倒退，也不会被提前跳到的步骤值压住。
`tests/progress-persist.mjs` 的【G2】同时锁住了"单调不倒退"和"末批正好走到 82% 与后续衔接"。

## 八、可配置项

| 配置键 | 默认 | 说明 |
| --- | --- | --- |
| `batchChapters` | 10 | 每批最多章节数 |
| `batchChars` | 30000 | 每批最多字数（与章数先到者为准） |
| `batchSummaries` | true | 每批生成 LLM 摘要；关掉只留确定性摘要 |
| `resumeBatches` | true | 是否复用已落盘批次（由服务端按 `resumeTaskId` 决定） |

新增 Step 名 `step-batch`，可单独挂生成预设后缀。

## 十一、无法在本沙箱验证的部分

- **真机长篇 + 真 LLM 的抽取质量**：这里全部用假 LLM，只能证明链路正确、
  归并不出错，不能证明"分批后抽取质量真的更好"。这需要真实长篇与真实模型。
- **超大长篇的内存占用**：批次结果全部留在内存里（`perBatch`）。
  110 章 / 12 万字量级没问题；如果喂 1000 章，`perBatch` 会累积很多小对象。
  真到那个量级应该改成"用时再读盘"，这里没做。
- **暂停的响应延迟**：最坏情况要等当前批次的 4 次 LLM 调用跑完（可能几分钟）。
  界面上显示"暂停中…"，但没有做"放弃当前批"的强停选项。
